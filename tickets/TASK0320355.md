## Confirmed via email

A separate ServiceNow comment thread on `RITM0298835` (subject line shows "Building Symbols," the RITM's
short description, though the comment itself is about the `HGTSOURCE` field on `BLD_building_polygon`):

> 2026-05-20 10:30:57 - Alex Gallagher, Additional comments (Customer Visible): "most pressing item: Add new field HGTSOURCE, alias Height Source"

Forwarded by Alex Gallagher to Lisa O'Toole shortly after: "There are other components to the ticket, but I was able to get the HGTSOURCE field added to the feature class."

**`HGTSOURCE` belongs to `BLD_building_polygon`, not `BLD_Building_Symbols`.** Confirmed by three independent
sources: this ticket's description above, `TASK0312692`'s description (`tickets/TASK0312692.md`), and the
standalone "Building Height in GIS" email thread (Lisa O'Toole → Cameron Robertson / Margie Pike, 2026-04-13,
no objections raised) which spells out the full field spec: `HGTSOURCE`, alias "Height Source", `TEXT(30)`,
domain `Bldg_height_source` (coded values `LIDAR`, `ECOPIA`, `PICTOMETRY`, `POSSE`). This also matches the
RFC's DATASET DETAILS tab (`changes/Changes to BLD_building_polygon feature class.xlsx`, row 26) and the
deployed `BLD_building_polygon_insp_VW` definition logged in `workflow.md`, which selects `HGTSOURCE` directly
from `BLD_building_polygon`.

**Resolved:** a historical script (`workstreams/bld_asset_point/scripts/completed/4_new_field.py`, uploaded 2026-08-20, run against Prod
only) targeted `SDEADM.BLD_building_symbol` with this same `HGTSOURCE` / `Bldg_height_source` field spec,
instead of `SDEADM.BLD_building_polygon`. No source ticket, RFC, or email calls for `HGTSOURCE` on
`BLD_Building_Symbols`, only `SYGROUP` (a different field, different purpose). Live ArcGIS Pro Fields views of
`SDEADM.BLD_building_symbol` in both QA and Prod (2026-08-20) confirm no `HGTSOURCE` field exists in either —
so whatever that script did, it didn't leave a stray field behind. Nothing to clean up.
